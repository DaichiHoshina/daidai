DD = DesignDoc。共通文章原則は [PRINCIPLES.md](PRINCIPLES.md) 参照。

## Design Doc の目的と完成条件

Design Doc は、要件を実現するための設計方針、技術的な判断とその根拠、影響範囲、リスクを明確にし、実装前に設計の妥当性について合意形成するための文書である。設計を記録することより、実装後に問題になりそうな点を実装前に見つけて解決することに価値がある。

- 記載範囲: 設計全体に影響する技術的な判断を記載する。利用者から見える振る舞いに限らず、整合性・排他制御・性能・セキュリティ・障害時の振る舞いなど、システムの成立に関わる判断も対象にする。具体的な実装方法は原則として詳細設計に分ける。特定の実装方式が設計の成立条件になる場合だけ、DD にもその判断と根拠を記載する
- 完成条件: 関係者が設計の妥当性を判断でき、実装に進んでよいと合意できる状態を完成とする。「実装に進んでよい」は、すべての技術的な課題が解決済みという意味ではなく、重要な設計判断が終わり、未解決の課題とその対応方針が明確になっている状態を指す。判定の項目は「完了判定の項目は要件の書かれ方を検査する」の 5 つの問い

## 前提: DDと詳細設計書は別物

混同するとレビュー不能になる。**書く前にWhyかHowかを判別する**。

| 項目 | Design Doc | 詳細設計書 |
|------|-----------|-----------|
| 主目的 | 設計判断の共有 | 実装仕様の定義 |
| 主読者 | エンジニア全体 / レビュアー / SRE / PdM | 実装者 |
| フォーカス | **Why / Architecture** | **How / Implementation** |
| 内容 | 背景・課題・選定理由・トレードオフ・非機能要件 | テーブル定義・API・SQL・バリデーション・シーケンス |
| 例 | 「なぜSKIP LOCKEDを使うか」 | 「SQLをどう書くか」 |

**DDD / マイクロサービス領域ではDD力 > 詳細設計力**。transaction / lock / idempotency / saga等は「実装」より「設計判断」が価値。

### Design Doc と作業計画書と Phase 詳細設計の境界

上の 2 文書を spec 型の流れに当てはめると、詳細設計書は作業計画書と Phase 詳細設計に分かれる。

| Design Doc に記載する | 作業計画書に記載する | Phase 詳細設計に記載する |
|---|---|---|
| 背景・課題 / 目的 / 要件 | Phase = PR と実装順序 | 変更 file / 関数・メソッド / 問い合わせ / 公開する契約 |
| 期待する振る舞い / API・DB・UI の変更 (何が増え、何が変わるか) | 触る層とその責務 | 契約 / TX / 排他 |
| 制約 / 非対象 / Acceptance Criteria | 完了条件 (どの test で確かめるか) | test の実装方針 |
| 設計上の重要な決定 (後から変えると設計全体に影響する判断) | 処理の置き場や共用の仕方 (後から変えても設計全体に影響しない作り方の決定) | データ移行の手順 / code レベルの詳細 |

判定基準は「後から変更すると設計全体に影響する判断か」。利用者から見える動きが変わるかだけで分けると、整合性や排他制御の方針が DD から外れ、設計レビューで確かめられないまま実装に進む。方針と、その実装は次のように分ける。

| Design Doc に記載する方針 | 詳細設計に記載する実装 |
|---|---|
| 整合性を保証する方針 | SQL・トランザクション境界 |
| 排他制御の採用方針 | ロックの取得と解放の具体的な方法 |
| 障害時の振る舞いと復旧方針 | リトライの条件・例外処理の実装 |
| キャッシュの整合性方針 | キャッシュを操作する具体的な命令 |

トランザクション境界やロック方式そのものが設計の成立条件になる場合は、DD でも決定事項として扱う。

- ただし **method の「存在」は Design Doc、どの Phase で作るかは作業計画書、method の「実装形」は Phase 詳細設計**
- 「発送手続き中の注文が指定サイズを採用しているか判定する読み取りが必要」までは Design Doc に記載し、その method 名・SQL・呼び出し元は Phase 詳細設計に記載する
- Design Doc に PR1 / PR2 のような分割は記載しない

### 画面の動きは DD で決めない

画面の遷移、操作の後に戻る画面、入力を別の画面へ移動させるかは UI/UX の判断で、デザインで決める。DD はこれらを決定として記載せず、次の形で扱う。

- 未定事項に置き、決める人をデザイナーと PRD の作成者にする
- その決定で工数が変わるなら、選択肢ごとの作業の違いを添える
- サーバーの判定や API がその決定に左右されないなら、そのことを記載し、デザインを待たずに作れる範囲を示す
- Figma などのデザイン資料があれば、決まっていることと決まっていないことを分けて記載する

### PRD に無い仕様を DD で決めない

利用者への知らせ、他部署の運用の手順、PRD に無い上限の追加、利用者に求める操作の回数は、PRD 作成者が決める内容になる。セキュリティ上よさそうに見えても、DD に決定として記載すると PRD 作成者の判断を先取りし、照合のときに取り下げの手戻りが大きくなる。

- 各「決めたこと」が PRD のどの記述に基づくかを確かめ、根拠が無いものは技術上の制約か PRD 作成者が決める内容かに分ける
- PRD 作成者が決める内容は未定事項に置き、BE が決めるのは API が返す status と理由の識別子までにする
- 仮の決定で進めるときは、概要・見出し・受け入れ条件のすべてに「仮の決定」と明記する (未定事項の表だけに書くと、他の節が決定済みに読める)
- PRD への確認は「〜という認識で大丈夫ですか？」の形で、今の PRD のままだとどうなるかを先に示す
- Slack などの古い発言は、PRD の変更履歴で置き換わっていないか確かめてから根拠に使う

## DDの6要素 (すべての項目を含む形は全部、軽量な形は該当分のみ)

テンプレは選択制 (軽量な形 5 節 / すべての項目を含む形 12 セクション、後述「テンプレ選択」)。すべての項目を含む形では 6 要素を全て書く。軽量な形では Why と失敗ケースを必須とし、残りは変更内容に該当する要素だけを Appendix 等で扱う (例: DB 変更がなければ移行戦略は不要)。

| # | 要素 | 内容 |
|---|---|---|
| 1 | **Why** | PRD / 要件との接続 (×「新テーブル作る」○「O(1) 抽選のため新テーブル作る」) |
| 2 | **比較とトレードオフ** | Alternatives必須、最低2案。設計は正解でなく選択 |
| 3 | **変更耐性** | 「今動く」でなく「変更しやすいか」 |
| 4 | **責務境界** | service / module間の役割 (DDD的、曖昧だと事故る) |
| 5 | **失敗ケース** | 在庫不足・API失敗・二重実行・再実行しても結果が変わらないことなど本番で障害になる点 |
| 6 | **移行戦略** | DB変更はExpand → Migrate → Contractの3段 |

レベル高い書き方: 数字で語る (O(n)→O(1)) / 図で説明 (シーケンス・ER・アーキ) / 制約明示 (DB のバージョンと isolation level)。

## DDと runbook / 実装 docsの役割分担

DDは **方針** を扱い、**具体閾値・実装値・運用手順** は別 doc (runbook / 監視設定 / 実装コメント) に委譲する。

| 種別 | 扱う内容 | 例 |
|---|---|---|
| DD | 段階分け / 監視意図 / 設計判断 / トレードオフ | 「監視は 3 段階 (当日 / 観察 / 運用)」「なぜこの metricを取るか」 |
| runbook / 監視 doc | 具体閾値 / 通知先 / 対応手順 | 「CPU 80% で alert、Slack 通知先は opsチャンネル」 |
| 実装コメント | 時系列の制約 / API 仕様 / 値の根拠 | 「timeout=2sは p99 + 余裕」 |

**重複検知**: 同じ事象がDDと runbookで具体値含め説明されていたら、DD 側を方針記述に縮め、runbookへリンクで委譲する。DD 内で「具体値は <runbook 名> 参照」と書く。

**Why**: DDで具体値を記載すると、運用調整で値変更時に DesignDoc も更新しないと一致しない。方針 (Why) と値 (How) を分離すると更新コストが値側だけになる。

**実装の内部構造も DD の外**: どの層がどの順で値を渡すか、既に読み込んだ行を再利用するか、test が期待値をどう定義するかは実装者が決める。DD には「判定に何を入力するか」「いつ決まるか」「何が失敗するか」までを記載する。代替案の比較表も仕様の選択肢で並べ、「読み込み済みを使う vs 再度読み込む」のような実装の書き方の対比を案として立てない。

**Why**: 実装の書き方は DD の承認後に変わるが、DD 側を更新しないので一致しない。仕様として満たすべきことだけ書けば、実装が変わっても DD は正しいままになる。

## 4 Step

| Step | 概要 | 具体 |
|---|---|---|
| 1. 着手前リサーチ | 既存資産・前提の事前確認 | 5観点 + PRD見出し対応表 |
| 2. 最初のバージョンの必須要素 | テンプレ通りに埋める | テンプレ / 用語定義 / アクターmatrix / 数値4点 / Rollback / 未決 / 監視1:1 / UTC-JST / 環境固有名詞 |
| 3. 完成前3段スキャン | 提出前セルフレビュー | 抽象bullet / 数値根拠 / 用語 → lint実行 |
| 4. レビュー対応 | コメント対応規約 | 1コメ = 1 commit、返信にcommit URL、textlint単独commit禁止 |

### Step 1詳細: 着手前5観点

| 観点 | 確認内容 |
|---|---|
| 既存ダッシュボード | 監視・SLOがすでにあるか |
| フラグ | feature flag / kill switchの有無 |
| 識別子実在 | 想定するID・キー・enumが実在するか |
| DB前提 | テーブル・index・制約・サイズ感 |
| 関連層影響 | API / Worker / Batch / 別serviceへの波及 |

### Step 2詳細: 数値4点セット

「規模・頻度・遅延・コスト」を最低でも記載。記載不可なら「未測定 / 推定 / 仮定値」と明示。

### Step 3詳細: 3段スキャン

1. **抽象bullet**: 「対応する」「整理する」等の動詞だけのbulletを発見 → 具体化
2. **数値**: 「多い」「速い」「遅い」を見つけ → 数値or範囲に
3. **用語**: 初出の専門用語に定義があるか / コードフェンス羅列がないか
4. **評価の独立性**: 「複数チェックがある」=「安全」と判定する前に、各チェックが独立した source / 観点を参照しているか確認する。同一値を 2 経路で参照しているだけなら1チェック扱い

## 本文と Appendix の階層分離

DD の本文 = 方針 / 判断 (レビュアー向け)、詳細表 = Appendix (実装者向け) の階層で分離する。

- **本文に記載する**: 設計判断 (Tradeoffs の比較表)、Schema (テーブル構造)、Invariants (守るべき不変条件)、Rollback、移行段取り。**レビューの核**
- **Appendix へ移動する**: Endpoints 全パス表 / Error Handling 全 status 表 / レスポンス enum 表 / 列名 ↔ UI 対応。**実装時に参照する詳細**
- API Design 節は「方針」と「status code の使い分け」だけ書き、一覧は「Appendix を参照」と誘導する

**Why**: レビュアーは「何を・なぜ (設計の意図・判断)」を読みたい。エンドポイント全パス・エラー status 全行・enum 表・file:line・request 構造体を本文に並べると、設計の筋が詳細の中で読めない。

## 散文から実装識別子を対象外にする (技術用語ちゃんぽん回避)

DD の読み手は実装するエンジニアなので、API path・欄の名前・設定やフラグの名前・table 名は、backtick で囲んで本文にそのまま使ってよい。初めて使う箇所に、何を指すかを 1 句添える (例: 「`loggedInAt` (セッションに保存したログインの時刻)」)。

- 和名へ言い換えるのは、言い換えが短い語で済むときだけにする。「再認証用の OTP の検証の失敗の回数」のように「の」が 3 つ以上続く和名になるなら、言い換えずに実装の名前を使う
- 冒頭の要約と受け入れたリスクの表は、PM や CS も読むので和名で記載する
- `.vue` file 名・関数名・status code 番号は、決定を実現する方法なので DD に記載せず、Phase 詳細設計に記載する

識別子を **literal として必要な場所** (Schema 定義 / Endpoints 表 / Error Handling 表 / Mermaid / 実装場所の指示 `<層の dir>/...`) には維持する。

**ちゃんぽん (ルー大柴) の回避**: 技術用語 (enum / feature flag 等) は literal で維持してよい。ただしカナで定着した語 (ロールバック / タイムアウト / リトライ 等) はカナへ開く (`PRINCIPLES.md` 「一般名詞の英語連結も開く」)。どちらの場合も「英語 + 和語」を 1 文で併用せず、どちらかに統一する。

- ❌ 「ON → OFF は常に無効にする」(disable を中途半端に和語化)
- ✅ 「ON → OFF は常に操作できない」(地の文は和語で統一)
- ❌ 「未選択 submit を防ぐ」
- ✅ 「未選択の送信を防ぐ」

判定基準: その英語が **識別子 / DB 用語 / API 用語 / 確立した技術語** なら literal でよい。一般動詞 / 一般名詞 (submit → 送信、disable → 無効 / 操作不可) を英語のまま地の文に使うとちゃんぽん。

### ちゃんぽんでない正当な混在

以下は「技術用語の literal + 日本語の助詞」で正常:

- 「`product_size_codes` への bulk INSERT を同一トランザクションで実行する」
- 「旧形式 fallback で受ける運用に切り替える」

## DD 圧縮ルール (雑音を削る)

DD 起草時 / 圧縮 review 時に該当箇所を削る。

削る:

- PRD と重複する背景説明は再掲しない。DD = 設計と運用、PRD = 要件と背景で役割を分ける
- PdM 回答の経緯は別 doc (local-docs 等) に置き、DD には決定事項のみ書く
- Open Questions は「判断が来ないと進めない」未確定論点のみ記載する。確定済 / 回答済の論点は削除する
- Non-Goals は「やらないこと」だけ列挙する。方針説明・既存機能・自明事項は書かない
- Scope は In のみ書き、Out は Non-Goals に集約する (sub-bullet で再掲しない)
- schema 設計は列定義 table (5 列表) に合わせる。DDL 全文は migration 実装者の範疇で DD に記載しない

削らない (判断記録 / 仕様として価値がある):

- Schema Design Tradeoffs (代替案比較 table) / Invariants / Endpoints table / 初出用語の 1 行解説

書式:

- 1 file に H1 は 1 つだけにする

## spec 型 DD (基本形): 実装から逆算して書く

DD を設計の説明ではなく **実装と検証の入力** として書く。節構成は下の「型の選び方」の順で決め、配置先に既存 DD も template も無いときに spec 型の節構成を使う。軽量な形 / すべての項目を含む形 / 分割型は、repo の規約や規模で節構成を変えたいときの選択肢になる。どの節構成を採用しても、この節の 4 原則は変わらない。

### 型の選び方 (配置先の既存 DD を最初に確かめる)

節構成を決める前に、DD を配置する dir を調べ、次の順で型を決める。読み手は同じ場所にある DD と同じ形を期待して読むので、template より配置先の実物を優先する。

1. 配置先と同じ dir (無ければ同じ repo の DD の dir) に既存 DD があれば、新しいものから 2 本読み、その構成と粒度に合わせる
   - 合わせるもの: 節の名前 / 見出しの言語と付け方 (名詞か文か) / 決定の書き方 (決定ごとの小見出しか表か) / 本文の行数 / 図と強調の使い方
   - 合わせないもの: 既存 DD の型に関係なく「読み物として読める構成」の規則に従う。決定事項は冒頭の節の直後に独立した節で配置する / 用語の節を本文の前に作らない / 決定に通し番号を振らない / 実装の名前は「散文から実装識別子を対象外にする」に従って本文で使う / 同じ事実は 1 か所に記載する。既存 DD がこれらと違う書き方でも、合わせると読み手が結論にたどり着くまでの前置きが長くなる
   - 行数は `wc -l` で実測する。書き上げた DD の行数が既存 DD から大きく外れたら、増えた節と減った節を既存 DD と比べ、理由を説明できない差を既存 DD に合わせて修正する
   - 見出しの付け方と強調の個数について、この file や template の規則と既存 DD が違うときは、既存 DD に合わせる。検査の warn (強調の頻度など) だけを理由に、既存 DD と同じ書き方の箇所や、user が確認した後の強調を書き換えない
2. 既存 DD が無く、repo に DD の template があれば、節の順序は template に従う (下の「repo に DD template があるとき」)
3. どちらも無いときだけ、spec 型の template の節構成で書く

1 と 2 のとき、spec 型の template は節構成ではなく要素の点検表として使う。目的 / 対象範囲 / 非対象 / 受け入れ条件 / 決定と理由 / 未定事項 が、採用した型のどこかの節に記載されているかを確かめ、無い要素は「repo に DD template があるとき」の位置へ加える。template にしか無い節 (変更面の表や合計の行など) は新しく作らない。

チームの共有文書 repo へ置くときの型の探し方 (直近の文書の読み方、ひな形を変える PR の確認) と、種類をまたいで共通する書き方は team-docs-conventions.md に従う。

型を途中で変えると全文の書き直しになるので、型は構成案の時点で決め、採用した型と根拠 (読んだ既存 DD の節構成と行数) を構成案に含める。

### 逆算の 4 原則

1. **完了の定義から始める**: 「実装が終わった」と言える条件 (受け入れ条件) を先に表で列挙する。**条件に ID を振らない。`AC-1` / `AC-001` のような label は PRD / DD / 作業計画書 / Phase 詳細設計のどこにも記載しない** (team の DD に ID の慣習が無く、見出しの番号引用は読む人を表へ戻らせる)。例外は作業計画書の「目的と実装の対応」の表で、1 つのセルに条件を並べるときだけ条件の文の頭に `No.1` `No.2` と上流の順番を添える (user 決定。番号は文と一緒に書き、番号だけで条件を指さない)。条件を後続のステップから指すときは、原文の文で引用し装飾しない (`NG-DICTIONARY.md` 「上流 doc からの引用」)。PRD の条件は PRD の番号 (A-n など) で参照 (番号の無い PRD なら条件の文で引用)して DD には書き換えず、DD には PRD に無い条件だけを記載する。DD の決定が PRD の条件と両立しないときは、その PRD の条件と理由を該当する決定に記載し、完成条件に影響する場合は受け入れ条件からその決定を見出しの語で参照する (どちらで完成とみなすかが読み手に決まらないため)。本文はこの条件を満たすための説明として記述し、どの条件にも対応しない節は削る
2. **実装者が迷う点だけ決める**: データ / API / 画面 / 権限 / 失敗時 / 移行 のうち、実装者が code を読んでも決定できない点を「決定事項」に記載する。実装の書き方 (層の分け方 / 関数名 / 読み込み済みの再利用) は含めない (「DDと runbook / 実装 docsの役割分担」)
3. **検証できない仕様は書かない**: 受け入れ条件は「〜のとき、〜が〜になる」の形で、test か手動確認で真偽が判定できる文にする。「適切に」「必要に応じて」を使わない
4. **後続のステップへ渡せる形にする**: 作業計画書が受け入れ条件を文の引用で Phase に割り当て、実装の完了報告が満たした条件を返し、計画との照合の review が条件ごとに実装と test の有無を確かめる。条件の総数と本文の説明が一致していることを完成前に確かめる

### user が仕様を理解できる文章

読み手は実装者だけでなく、機能を決める user 本人でもある。

- **振る舞いは「誰が / 何をすると / どうなる」で書く**: 主語を user か system の具体名にし、1 文に 1 つの結果だけ書く (例「管理者が在庫を 0 にすると、商品一覧はその商品を表示しない」)
- **識別子は必要な箇所だけ本文で使う**: 対象を一意に示すために必要な table 名 / column 名 / endpoint は本文で使い、初出で何を指すかを 1 句添える。長い定義と識別子の対応一覧だけを Appendix に記載する (「散文から実装識別子を対象外にする」)
- **用語は初出で開く**: 略語と社内用語は本文で初めて使う箇所で 1 行説明し、1 行で足りない語だけを Appendix の用語の表に記載する。説明した後は同じ語だけを使う
- **前提 → 結果の順に並べる**: 条件が複数あるときは、条件を先に並べてから結果を記載する。例外や境界 (0 件 / 上限 / 同時実行 / 再送) は通常の振る舞いの直後に下位 bullet で記載する
- **段落より箇条書き**: 振る舞いと決定事項は bullet + インデントで記載し、採用理由や処理の経緯のうち、因果で順につながり論点ごとに分けると意味が切れる説明は段落で記載する (`PRINCIPLES.md`「markdown 長文 doc の 1 文 1 行 + 下位 bullet」)

### repo に DD template があるとき

repo に Design Doc の template (例: `.claude/docs/design/template.md`、DD を docs repo に保存するならその repo の `DesignDocs/template*.md`) があれば、節の順序はその template に従う (repo 固有規範が優先)。ただし書くことの無い節は作らない (「該当なし」だけの節は読み手の負担になる)。spec 型の要素は次の位置に差し込む。

- 決定事項: 最初の節 (概要 / Overview) の直後に、独立した `##` の節として配置する。template のデータモデル / API 設計 / Data Flow などの節の中に入れない (決定が別の話題の節の中に入ると、読み手が決定を見つけにくくなり、目次の問いと中身も一致しなくなる)
- 受け入れ条件: 決定事項の節の直後に配置する
- 用語: 独立した節を本文の前に作らない。新しい語は本文で初めて使う箇所で 1 行説明し、1 行で足りない語だけを Appendix の用語の表に記載する
- 未決事項: template に該当節が無ければ末尾へ追加する。検証の表 (受け入れ条件 / 設計上の対応 / 検証方法) は `--type full` のときだけ書く。spec 型では検証節を置かず、どの test で確かめるかは作業計画書の完了条件と Phase 詳細設計のテスト観点へ送る
- 識別子と和名の対応の表: 言い換えた語があるときだけ Appendix に作る (本文では実装の名前をそのまま使う)
- PR 分割と実装順序は DD に記載せず作業計画書に記載する。DD の Appendix には作業計画書の path だけを記載する (team の DD で PR 分割を DD に含めた例と含めないと明記した例が割れているため、sdd 系の流れでは後者に合わせる)

## テンプレ選択

| パターン | 状況 | 行数目安 |
|---|---|---|
| **spec 型・単ファイル (基本形)** | 実装に進める案件全般。受け入れ条件の表を軸に記載する | 本文 ≤ 300 (用語表 / Implementation Surface の表 / Appendix / `<details>` は別枠) |
| **軽量・単ファイル** | 小〜中機能、AI生成前提、レビュー負荷下げたい | ≤ 300 |
| **フル・単ファイル** | 大規模変更、セキュリティ影響、複数ドメインにわたる | ≤ 800 |
| **分割型ディレクトリ** | 新サービス立ち上げ・大規模プロジェクト | 各 ≤ 400 |

**配置先に既存 DD も template も無く、迷ったら spec 型から開始** → 設計判断が多く比較や移行の説明が膨らむときだけフル / 分割へ昇格する (昇格しても受け入れ条件の節は維持する)。既存 DD か template があるときは「型の選び方」に従う。

### 軽量な形のテンプレ (5節)

```text
## Overview        # 何を実現するか / Issue・PRD リンク (Spec があれば受け入れ条件の対応表を直下に置く)
## Data Flow       # シーケンス図 / 主要フロー

## API Design      # エンドポイント表
## Appendix        # 代替案 / 未決事項 / 関連リンク
```

### すべての項目を含む形のテンプレ (12セクション)

Overview / Goals & Non-Goals / Background & Spec 対応 / High-Level Design / Detailed Design / Alternatives / Trade-offs / Invariants & Failure Handling / Migration Plan / Rollback / Verification & Observability / Open Questions

#### 初稿に抜けやすい section の補強基準

- Background & Spec 対応: Spec / PRD がある案件では、受け入れ条件を 1 行ずつ「受け入れ条件 / 設計上の対応 / 検証方法」の 3 列表へ書き下す。Spec の内容をここで再説明しない
- Invariants: 常に守るデータ整合性、同時実行と再送で成立させる条件、書き込み時に再検証する条件を分けて書く。失敗時に戻す状態と維持してよい状態を対にする
- Verification & Observability: リリース前の検証とリリース後の監視を別 sub section に分ける。前者は Spec 対応表の各行をどの test で担保するかを書き、後者はログ / メトリクス / アラートの 3 階層で書く
- High-Level Design: SVG で手描きした構成図を 1 つ以上入れる。図は SVG で手描きし、GitHub と repo 内の markdown では PNG に変換して画像で埋め込む (手順: `guidelines/writing/pr-description.md`「図の埋め込み方」)。HTML では inline SVG にする。図を描く前に diagram.md を必ず Read する
- Migration Plan: Expand / Migrate / Contract の 3 段で書く (「3 段階で進める」だけでは不足)
- Rollback Strategy: Phase 別の戻し方 table を書き、無停止 / 部分停止 / 元に戻せない、のどれかを明示する
- Observability: ログ / メトリクス / アラートの 3 階層で書く (ログのみは不足)
- Trade-offs: 「短期影響 vs 長期影響」の軸で書く (例: 短時間の停止を受け入れるか、長期の保守コストを抱えるか)。軸のない pros / cons の羅列は判断材料にならない

## 読み物として読める構成 (見出し・入れ子・表・強調)

見出し・入れ子・表・強調・語・書いた後の確かめ方の共通の規則は `document-design.md`「5. 判断を伝える文書の構成」が正本で、DD もそれに従う。ここには DD だけに当てはまる規則を記載する。

- 冒頭 (最初の節。既存 DD の型で書くときは概要の節の先頭) に、次の項目を見出し語つきの箇条書きで記載する。背景の説明から書き始めない
  - 目的: 誰の、どの状況を変えるのかを 1 文で
  - ゴール: この DD が合意されたときに決まっている状態を、達成を判定できる形で
  - 決めること: 決めた内容を言い切る文で記載し、問いの形にしない。区分と並びは決定事項の一覧と同じにし、決定が 6 件以上なら「区分 / 決めること」の表にまとめる (冒頭と一覧の件数や順が一致しないと、読み手は対応を探して往復する)
  - 決めないこと: 対象外にすることと、別の文書や後の工程で決めること
  - 変わること: 対象 (操作・画面・利用者の種類) が 2 つ以上あるときは、「対象 / 今起きていること / 変えること / 変更後の状態」の表を目的の直後に記載する。読み手が知りたいのは何が問題で、何を変えて、どうなるかで、決定の節はこの表をどう実現するかの説明として読まれる
- 本文の節には、決めたことと理由 (却下した案と受け入れる制約を含む) だけを記載する。今の作りは、決定の理由として必要な 1 文だけを理由の中に記載し、節ごとに背景の小見出しを作らない
- 決定は「何を保証するか」「利用者から見て何が変わるか」の言葉で記載する。決定を実現する方法 (呼び出す命令、保存に使う鍵、error の識別子、環境変数や設定値の名前、処理の順序) は本文に記載しない。決定の対象を指す名前 (API・画面・table) の書き方は、「散文から実装識別子を対象外にする」と「型の選び方」に従う
- 決定の仕組みが文だけでは読み取りにくいときに限り、処理の起点 (利用者の操作・API の呼び出し・バッチの起動) から完了までを、利用者とシステムの境界で観測できる出来事の順に番号付きの手順で記載してよい。関数や命令の呼び出し順は Phase 詳細設計に記載する。順序図がある流れは手順で繰り返さず、手順の番号を他の節から引用しない
- 取り違えると判断を誤る似た概念が 2 つ以上あるときは、違い (例: 役割・期限・使い終える条件) を表で比べる。違いが無い、または 1 つしか無いときは表を作らない
- 決定の理由に必要な背景 (今の作り) は、末尾の付録に集める。実装の方法 (命令 / 鍵 / status の番号 / 処理の順序) は付録にも記載せず、Phase 詳細設計に記載する。付録は全体を 1 つの折りたたみ (`<details>`) で囲み、その中に別の折りたたみを作らない。付録の中は「今の作り / 用語と実装の名前 / 参考」のように見出しで分け、本文の決定と同じ順に並べる。同じ内容を付録の 2 つの見出しに記載しない
- 冒頭に「決めること」の一覧 (決定の見出しへのリンク) があるときは、目次を作らない。どちらも節へ移動するための案内で、両方あると同じ役目の一覧が 2 つ並ぶ
- 目次を作るときは、大きい節 (`##`) だけを並べ、小見出しは含めない。項目は冒頭のゴールと同じ順に並べ、その節が答える問いの形 (「〜をどう守るか」) で記載する
- 要件は PRD にあること、細部は作業計画で決めること、今の作りは末尾の付録にあること、実装の方法は Phase 詳細設計で決めることを、GitHub の注記の枠 (`> [!NOTE]`) で示す
- 本文は折りたたまず、文字の装飾と区切りで読み分けられるようにする。折りたたむのは末尾の付録だけにする
  - `##` の節の間を区切り線 (`---`) で区切る
  - 冒頭の主な決定の一覧は番号付きの太字にし、各項目から決定の見出しへリンクする
  - 未定事項の表の前に、判定を有効にする前に決める事項であることを重要の枠 (`> [!IMPORTANT]`) の 1 文で示す
- 未定事項は、推奨を置けない事項 (画面の動きなど) だけを、共通の規則の「事項 / 決まったときの影響 / 決める人」の表にする
- API や設定の名前の書き方は「散文から実装識別子を対象外にする」に従う。言い換えた語があるときだけ、付録の「用語と実装の名前」の表で対応させる
- 節の順序は、冒頭 → 決定事項 → 受け入れ条件 → 振る舞い・対象範囲 → リリース → 未定事項 → 付録にする。既存 DD の型で書くときも、既存の見出し名を使いながらこの順序にする。決定事項を Data Flow や API Design などの節の中に入れない
- 用語の節を本文の前に作らない。新しい語は初めて使う箇所で 1 行説明する
- 決定事項の一覧は、本文の決定の節と同じ順に並べる。区分で分けるときは、本文の決定の節も区分の順に並べる
- API の一覧 (メソッド・パス・判定) は、判定を示す表 1 か所にまとめる。決定の本文と API の節は、その表を参照し、新しく作る API だけを API の節に記載する
- 未定事項に当たる分岐を図や表に記載するときは、分岐の先を「未定事項」とし、決めた動き (実行する / 止める) に見えるようにしない
- 同じ事実を記載するのは 1 か所だけにする。数値・期限・回数・リリースの順番は決定事項の節だけに記載し、受け入れ条件・データ・リリース・未定事項では値を書き直さず、決定の見出しで参照する。冒頭の要約だけは値を記載してよい
- 確認先の回答を待っている決定は、決定として記載し、未定事項の表に重ねて記載しない。確認先と決まったときの影響は、その決定の補足に 1 行で記載する
- 「却下した案」には案の名前だけを記載し、却下の理由が同じ決定の「理由」と同じなら繰り返さない。理由に無い却下の根拠があるときだけ、案の後に 1 文で記載する
- 受け入れ条件の表を、決定の「決めたこと」の言い直しにしない。冒頭に「各決定の『決めたこと』もすべて満たす」と 1 文で記載し、表には、決定の文だけでは確かめ方が分からない条件 (同時に来た 2 件、セッションの作り直しの後、フラグが無効の間など) だけを記載する
- 受け入れ条件の表の 1 行は、確かめる対象を 1 つにする目安にする。操作が 2 つ以上、または成功する場合と失敗する場合が 1 行に含まれると、読み手はどの確認が満たされなかったかを特定できない。同じ要求と同じ前提の続きの確認 (同じ記録で 2 回目を呼ぶ場合など) は 1 行のままでよい。この判断は script でなく review が行う
- 定義 (「登録済み」の範囲など) と、複数の決定で使う理由は 1 か所に記載し、他の節は節の名前で参照する。片方だけ更新すると内容が一致しなくなる
- 画面や API の一覧の表では、内容の列に決定の言い直しを記載せず、その画面や API に固有の違い (開く場面、呼ぶ API) だけを記載する。同じ内容の行は 1 行にまとめる
- PRD の記載と違う決定は、受け入れ条件の冒頭に列挙せず、その決定の「却下した案」に PRD の記載と理由を示す。完成条件に影響する場合は、受け入れ条件からその決定を見出しの語で参照する
- 決定に「決定 1」「決定 2」の通し番号を振らない。参照するときは決定の見出しの語で指す (番号だと、読み手は番号の決定を探して前後を行き来する)。見出し語で参照するので、判断・事項・用語の表の 1 列目は、同じ表の中で重ならないようにする。似た判断が 2 行あるときは、比べる相手を括弧で添えて区別する (`dd-gate.sh` の `dup-row-name` が検出する)
- 既存 DD の型で書くときは、見出しの付け方と強調は既存 DD に合わせる (「型の選び方」)。この節の冒頭・本文・付録・目次の規則は、型に関係なく適用する

|---|---|---|
| Overview / 監視 / 検証結果 / 結論 | PM / 他チーム engineer / SRE / QA | 日本語優先 (専門用語は初出で平易化) |
| Phase 詳細設計 / 並行制御 / DB 内部 / SQL | 同領域 engineer / レビュアー | 英語慣用 OK (locking read / MVCC snapshot 等) |

**判断**: section 冒頭で「この sectionは誰が読むか」を 1 秒で判定して用語層を採用する。同section 内での揺れは禁止 (同じ単語が日本語と英語で混在する状態は最悪)。

## 未決事項の書き方

「項目 + 決定方法」を対にして書く。決定方法が未定の論点も表から削除せずに記載し、不明な欄は「未定」として、設計への影響と次に確認することを示す。重要な論点の対応方針が決まっていない場合は、実装に進む合意がまだ成立していないことを明記する。

- 1 行は 1 つの論点にする。決める人と決まったときの影響が論点ごとに違うので、複数をまとめると、列に答えを記載できない。この判断は script でなく review が行う
- 本文から参照するときは、表の行の見出し語 (事項の欄の先頭の名前) をそのまま使い、「未決事項「〇〇」」の形にする。「10 の 4」のように番号で参照すると、読み手は表を上から順に確認して探すことになる (`dd-gate.sh` の `numeric-ref` が検出する)。順序図の番号を図の直下で参照するのは `diagram.md` の規則どおりで、この対象に含めない

| 本文に記載する | 未決事項に記載する |
|---|---|
| 合意済みの方針 | 合意前の提案 |
| コード・計測で検証済みの事実 | 仮定・推定 |
| 今回やること | 別issueでやること |

## DD を短く保つ一般の原則

社外の設計書の書き方で共通する原則のうち、DD の長さに関わるもの。

- 修正のたびに不要な文を削る。古い文を含む長い文書より、少数の新しく正確な文書のほうが使われる (Chromium の Documentation Best Practices「alive but frequently trimmed」)
- 本文の中心はトレードオフ (なぜこの案が目的と対象外の範囲に合うか) にする。実装の手順書になる部分は DD に記載せず、作業計画書に記載する (Industrial Empathy「Design Docs at Google」)
- 曖昧さが無く、トレードオフを比べる場面も無い変更は、DD を作らずに PR の本文で説明する (同上)
- 実装を始めた後に決定が大きく変わるときは、本文を書き換えたうえで、変わった決定を ADR (決定ごとの短い記録) として別の文書に記録し、DD の冒頭からリンクする。ADR は承認後に書き換えず、変わったら新しい ADR を作って古い方の状態を「置き換え済み」にする (Martin Fowler「Architecture Decision Record」、AWS の ADR process)。DD を変更の記録の置き場にしないので、DD は今の決定だけを保つ

## 完了判定の項目は要件の書かれ方を検査する

DD を作業計画へ進める前の完了判定は、実装の振る舞いでなく要件の書かれ方を検査する。判定は次の 5 つの問いで行い、すべての観点に詳細な検討結果を記載することまでは求めない。

| 順序 | # | 問い | 判断したいこと |
|---|---|---|---|
| 正しさ | 1 | 要件を満たせるか | 正常系と異常系で、期待する動作を実現できるか |
| 正しさ | 2 | 技術的に成立するか | 整合性・排他制御・性能・セキュリティ・障害時に破綻しないか。観点を並べるだけでなく、設計を破る場面 (同時の要求、古いキャッシュ、途中での失敗) を探し、破られない理由か対策で示す |
| 妥当性 | 3 | なぜこの設計が適切なのか | 代替案と比べ、トレードオフを許容できるか |
| 妥当性 | 4 | 既存システムにどんな影響があるか | 既存の機能・データ・運用への影響を把握しているか (該当しない観点は「該当しない」の 1 行でよい) |
| 実装可能性 | 5 | 実装に進める状態か | 重要な判断が終わり、未解決事項の対応方針と解決する工程が決まっているか |

- 確かめる順序は、正しさ (1・2)、妥当性 (3・4)、実装可能性 (5) の順にする。正しくない設計の妥当性は比べる意味が無いので、1・2 で破綻が見つかったら 3 以降に進まない
- 各問いには、結論 (何を判断したか)・根拠 (なぜそう判断できるか)・未解決事項 (まだ何が分からないか) の 3 つで答える。「問題ありません」だけの答えは判定に使わない。たとえば問い 2 なら、「整合性に問題なし」でなく、キャッシュの更新と認証の処理が競合したときの動作とその根拠で答える
- 問いを満たすこと自体を目的にしない。目的は、設計が要件を満たし、技術的に成立し、採用する合理的な理由があり、既存システムへの影響と未解決のリスクを理解したうえで、実装に進む判断ができることにある
- この 5 つは Design Doc に固有の完成条件で、PRD・作業計画書・Phase 詳細設計には、それぞれの工程の完成条件を使う

各項目の書き方は次のとおり。

- 誤: 「一覧に 3 件表示されるか確認する」 — 実装を動かさないと判定できず、Design Doc の段階では答えが無い
- 正: 「表示件数と並び順が明示的に指定されているか」 — Design Doc の本文だけで判定できる
- 判定基準: 各項目が `Is X clearly specified?` の形に書き換えできるか。書き換えできない項目は実装の検査が含まれているので、作業計画書より後の工程の判定へ渡す

## PRD と PR コメントの優先順位 (SoT の扱い)

**Rule**: SoT (真の値) は PRD。だが PRD 本文が PR review や朝会で決まったことを反映しそびれるケースがある。整合性チェックで PRD と DD が一致しなかったら、**PRD 本文だけでなく PRD 側の PR コメントも必ず読む**。PR コメントが真の確定事項のことがある。

**Why**: PRD 本文だけ見て整合性を判断すると方向を誤る。実際に「PRD が古く、PR review コメントで PdM が方針を変えた」ケースで Critical の方向を逆に判定した事故がある。

**How to apply**:

- 整合性チェックで食い違い発見時: `gh pr view <N> --comments` で PRD PR のコメントを確認。inline も `gh api repos/.../pulls/<N>/comments` で読む
- PRD 修正は PdM 領域。DD に「PRD のここを修正する必要がある」節を作らない。食い違いは Slack / PR コメントで PdM に伝える
- 役割分担: PRD = 要件・背景 (PdM 管理) / DD = 実装方針 (エンジニア管理) / Figma = UI / PR コメント・朝会ログ = PRD 反映が遅れたときの真の決定源
- 実装詳細 (PRD に縛りがない範囲) は DD 側の設計判断で確定してよい

## 複数の出典が一致しないときの推奨

複数の出典で同じ要求が違う言い方をされていたら 1 つにまとめ、一致しなければ両方を記録して未確定点に上げる。推奨は次の順で決め、断定でなく「推奨」として記載する。

- 同じ人の発言どうしなら、新しい方を推奨にする
- 別の人どうしなら、依頼元 (起票者 / PRD author) の発言を推奨にする
- 日付の無い出典は新旧比較の根拠にせず、「日付不明」と記載したうえで日付のある発言を推奨にする
