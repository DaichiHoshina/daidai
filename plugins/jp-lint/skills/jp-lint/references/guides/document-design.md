# 文書作成の共通規則 (章立て・書き直し・図)

<!-- writing-tree: parent=PRINCIPLES.md role=content -->
<!-- writing-tree-required: 1. 手法・仕組みの紹介文書の章立て | 2. 既存の文書を書き直すときの規則 -->

人が読む文書を作る・書き直すときに、媒体 (Notion のページ / HTML の Artifact / local-docs の HTML / md / 記事) によらず従う規則。媒体ごとの見た目と書き込みの手順は、媒体の skill (`update-notion-page` / `create-local-doc` / `create-tech-article` など) が扱う。文と語の規則は `PRINCIPLES.md`、長文の種別ごとの規則は `long-form-doc.md` にある。

## 1. 手法・仕組みの紹介文書の章立て

手法や仕組みを紹介する文書 (Notion のページ / HTML の Artifact / 記事) は、媒体によらず次の順で章を構成する。読み手は「読むかどうか」を先に決め、細部は使うときに読むので、判断に必要な情報を前に、細部を後ろに配置する。

| 順 | 章 | 中身 | 読み手の問い |
|---|---|---|---|
| 1 | 冒頭 | 目的と、この手法に固有の特徴を 2〜4 文。直後に工程の図 (線路図) | 全体として何をするか |
| 2 | 概要 | 方針の要点と、変更の規模ごとに使うかどうかの表 | 自分の作業で使うべきか |
| 3 | 理由 | 課題と対応の表。課題は実際に困った事実で書く | なぜこの進め方か |
| 4 | 一般的な手法との違い | 比較の表 | 既存の手法と何が違うか |
| 5 | 仕組みの要点 | 3〜5 項目。文書・コマンドの役割の表はここに配置する | どう動くか |
| 6 | 用語 / 付録 | 用語の定義 (折りたたみ)、コマンドの一覧など本文から参照されない詳細 | 細部を調べたい |

違いを仕組みより前に配置するのは、独自の部分を知ってから細部を読めるようにするため。

図は依頼が無くても描く。書き終えた章ごとに、次のどれかを文だけで説明していないかを確かめ、当たれば `diagram.md` を Read してから SVG を手描きする。

- 工程や処理の流れ (どの順に何が渡るか)
- 判定と分岐 (条件を満たさないとどこへ戻るか)
- 時間の経過 (最初に 1 回 / Phase ごとに繰り返す など)
- 2 つの案や手法の違い (どの矢印が増える・消えるか)

文 1〜2 行で伝わる内容や、比較の表で足りる内容には描かない。図の中の文字は短い名詞句にし、説明の文は図の前後の地の文に記載する。

見出しの文は、話題の名前 (「PR について」) ではなく、その節の主張 (「PR はレビューのしやすさを優先して分ける」) にする (`PRINCIPLES.md` 「文書全体の読みやすさ」の 8)。

- 工程の図 (線路図) は冒頭の文の直後に置き、補足に回さない。読み手は流れを知ってから課題や仕組みを読む
- 手法に固有の特徴 (他の手法に無い工程など) は、冒頭の文で 1 度紹介する。後半の章で初めて登場させない
- 本文の理解に必要な説明 (図に含まれる文書の意味、独自の工程の中身など) は付録やトグルに移さず本文に記載する
- 各章の頭には、前の章とつなぐ 1 文 (「1 章の 3 つの課題に対して〜」) を記載する
- 1 つの事柄は 1 つの章だけが説明する。全体の流れの章が役割を説明した文書やコマンドは、特徴の章では工夫した点だけを記載し、役割を言い換えて繰り返さない。課題と対応の表の「対応」列は 1 行程度にとどめる
- 課題が抽象的で、読み手が自分の作業に当てはめにくいときだけ、具体例の章を設ける。架空でよいので 1 つの機能を題材にし、各文書に何を記載するかを表で並べる。題材は書き手に確かめ、実在の未公開情報は記載しない。課題が実体験の言葉で書かれていれば、具体例の章は設けない
- 具体例の表の各行は、前の行と範囲を一致させる。前の文書で決めた範囲の外まで、後の文書の例が及ばないようにする。条件や基準の例には、読み手が判定できる中身 (何をもって条件を満たすか) まで含める
- 同じ語 (「設計」など) を複数の段階で使うときは、段階ごとに何を決めるかを同じ箇所で並べて示す。前の章で決めると記載した事柄を、後の章で別の時期に決めると読める形で記載しない
- 仕組みの説明は、何を配置するかより先に、何を防ぐための仕組みかを記載する。次へ進む基準は、道具の出力との一致ではなく、人ができる状態 (自分の言葉で説明できる など) で記載する
- 比較の表の比較軸は、特徴の章の項目と対応させる。他の手法の欄は「標準の工程で扱うか」の形で記載し、仕組みが無いと断定しない
- 抽象的な呼び名 (工程の出口 / 上流と下流 / 実装の形 / 判断の分かれる点) は、具体的な文書名や動作に置き換える (例:「工程の出口」を「各文書を作った後に確認の command を実行する」に置き換える)。規則を記載するときは例外 (後の工程で問題が見つかったら前の文書を修正する) も 1 文で添える
- 数値の基準 (行数の上限など) は、必須か目安か、他の条件とどちらを優先するかを同じ文で示す
- 表の行の見出しは、分類の記号 (「汎用 + 固有」) ではなく、確認する中身の名前 (「設計と品質」) にする。判定項目の一覧や手順の細部は載せず、定義 file を正本にする

## 2. 既存の文書を書き直すときの規則

媒体 (Notion / HTML / md / 記事) によらず、既にある文書を作り直す・短くする・一部を修正するときに従う。

- 本人が手動で編集した内容があるページを作り直す・書き直すときは、その内容を元にして、規則に合わせて加える内容だけを差分として書き加える。本人が書いた文の文体 (敬体か常体か)、実際に困った事実として書かれた課題、手法に固有の仕組み (独自の表や手順) は、一般論に書き換えず維持する
- 「短く」「重要な部分だけ」と頼まれたら、先に章をまたいだ重複と、見出しや図と同じ内容の文を削る。手法に固有の仕組みを説明する節は、重複が無ければ削らない
- 短くなる行数や減る件数のような修正の効果は、修正を適用した後に、修正前後を `wc -l` などで実測した数で伝える。適用する前に伝えるときは、削る行を 1 行ずつ列挙して集計した数にし、「適用前の見込み」と添える。重複して見える箇所の数から概算した数は伝えない
- 社内で共有する手順や仕組みの文書には、書き手の自己評価・感想・効果の主張 (「こだわったところ」「〜しやすくなります」「やり直しが減りました」) を記載しない。仕組みが何をするかと、その目的だけを記載する。記事など個人の発信を元にするときは、該当する文を削除するか事実の文に書き換える
- 箇条書きの階層は 2 段までにする。3 階層目が必要になったら、案内の 1 文と平らな箇条書きに組み替える

- 同じ題材の資料が別の媒体にもある (Notion のページと HTML の Artifact など) ときは、章立てと中身をそろえる。片方で章を組み替えたり、事実や表現を修正したりしたら、もう片方にも同じ修正を加え、加えなかった差分は理由と一緒に報告する

### 一部を修正した後の確認

一部だけを書き換えたら、文書全体を上から読み、次の 4 点を確かめる。修正した文だけを読んで終えない。

- 言い回しを変えた主張 (基準・目的・呼び名) が、冒頭・表・比較の欄など他の箇所で古い言い回しのまま記載されていないか。見つかったら同じ言い回しにそろえる
- 節に内容を追加した後も、見出しが節の中身全体を表しているか。別の話題が入ったら、見出しを変えるか、その話題を扱う節に記載し直す
- 表に行を追加したとき、同じ内容を表の前後の地の文でも記載していないか。重なる文は削除する
- 表や節を分けたり並べ替えたりしたとき、数を含む前置き (「3 つの表」「次の 5 項目」) と、他の箇所からの参照 (節番号・行の名前) が実際と一致しているか。一致しなければ前置きと参照を書き換える

### 変更不要と判断する前の確認

見出しがある file で「問題なし」とする前に、次を省略しない。確認結果は内部で使い、user が求めない限り工程として報告しない。

- 同じ結論や理由を別 section が言い換えていれば、所有先へ集約する。修正後に同じ主張の文が 2 つの section に残っていないかを読み直し、所有先以外は削るか、所有先への参照 1 文 (例: 「理由は「比較」節を参照」) に置き換え、主張そのものを要約し直さない。接続語 (「結論として」等) を消すだけでは集約にならない
- 完成稿で `当初` / `初期の説明` / `訂正` / `追加調査` / `再調査` / `誤りだった` / `不正確だった` を Grep し、各 hit が現在の判断に必要な証拠か、執筆・調査の経過メモかを判定する。後者が 1 つでも該当する場合は変更不要としない
- `<!-- type: decision -->` または decision 文書では、本文を「決定する問い / 判断を変える証拠 / 選択肢 / 比較 / 推奨または決定 / 未決事項」に分類する。調査順序や訂正文は investigation か `<details>` へ移動する
- 対象 file がローカルリンクで関連文書を参照するなら、現在の file 単独で「問題なし」と判断しない。リンク先の metadata・タイトル・見出し・正本表記を読み、重複した結論 / 同じ論点への異なる正本表記 / status と本文の不一致 (`status: approved` の未決表現) があれば、単語修正ではなく構成上の問題として扱う (`long-form-doc.md` 「文書セット設計」)。字数・節数・短文化のノルマはこの確認に追加しない

Grep の hit 数や section 数だけでは書き換えない。ADR / RCA に必要な履歴や、別概念を意図した用語は維持する。

## 3. 会議や定例で使う資料の構成

議題・ミーティング・打ち合わせの準備に使う資料は、媒体によらず、作り始める時点で構成を決める。本文の作成後に構成を変えると、詳細・リンク・図を追加する往復が 1 回ずつ増える。

- 先頭の章を「決めたいこと」にし、項目・推奨・決まらないときの影響を 1 行ずつの表にする
- 続けて、項目ごとの詳細 (各小見出しの先頭に結論 1 行、続けて今の状態・理由)、関連、の順に並べる。採らなかった案・未確認の点・想定される質問と答えは、会議の判断に影響する場合だけ含める。この種類だけは章の数の目安を超えてよい
- 本文で触れる issue・PR・コメント・PRD・code はすべてリンクにする。code は commit 固定の permalink にする
- 仕組みや攻撃・処理の流れが論点なら、図を 1 枚配置する
- 件数や状態は、作成する直前に元の issue から取り直す。作成中に他の人が更新することがある


## 4. 文字の濃淡と強調

本文を記載するとき、読む順番が濃淡で分かるように、次の 4 段を使い分ける。強調する箇所を結論と守る条件だけにする原則は `PRINCIPLES.md`「文書全体の読みやすさ」の 9 が正本で、ここでは段ごとの使い分けと個数の上限だけを決める。段ごとの記法は媒体ごとに決める。

| 段 | 使う箇所 |
|---|---|
| 濃い (太字) | 各節の結論の語句、判断に使う数値、読み手が守る条件。1 つの箇条書きや段落で 1 か所まで |
| 核心 (下線マーカー) | 文書全体の結論の 1 フレーズ。1 つの節で 1 か所まで |
| 注意の枠 (コールアウト) | 決め方しだいで結論の数字や判断が大きく変わる前提、読み手が決めないと先へ進めない論点。1 つの節で 1 つまで、文書全体で 3 つまで |
| 薄い | 前提・注記・出典・集計方法の補足のように、結論の後で読めばよい文 |

- 表の中では、合計の行と、結論で引用する値だけを太字にする
- 文全体や段落の丸ごとの太字は避ける (`PRINCIPLES.md`「文書全体の読みやすさ」の 9)
- 「前提」「まだ確かめていないこと」のような節では太字を使わない。太字にするのは、結論の数字を変える条件だけにする
- 結論の数字を変える前提 (増える・減る方向の注意) は薄くしない。薄くするのは、丸めの説明や参照先の節番号のような、読まなくても判断が変わらない文だけにする
- 下線マーカーを使うのは、文書の主題に答える文だけにする。主題から外れた補足の数値には使わない
- 注意の枠は、箇条書きの 1 項目に埋めると読み手が気づかない前提に使う。枠の見出しは「何で何が変わるか」を言い切る形にし (例: 「〇〇の定義で回数が変わる」)、本文には変わる向きと大きさを記載する。ふつうの注記や補足は枠にせず、箇条書きか薄い文字にする
- 注意の枠は、その前提で値が変わる表や図の直後に配置する。前提の章にまとめて記載すると、表を読む時点で前提に気づけない

## 5. 判断を伝える文書の構成 (見出し・入れ子・表)

見出しが複数あり、読み手が判断や作業に使う文書 (設計書 / 要件 / 作業計画 / 調査や比較の報告 / 長い PR 本文) に適用する。文単位の誤読の検査に合格しても、同じ型の箇条書きや長い段落が並ぶと、読み手は何を言いたい文書なのかをつかめない。文書の種類ごとの追加の規則は種別の guideline にある (設計書は `design-doc-protocol.md`「読み物として読める構成」)。

### 冒頭で結論を言い切る

- 最初の節に、文書全体の結論を太字の見出し語つきの数行で記載する。見出し語は、読み手が読み終えた後に答えられるようになる問い (何を解決するか / どう解決するか / 何が変わるか / いつ切り替えるか) にする
- 数値や種類が並ぶ結論は、1 行に詰めず下の階層の箇条書きに分ける
- 判定や分岐の流れの図は冒頭の節の中に配置し、図の上に図が答える問いを 1 行で記載する (図の規則は `diagram.md`)

### 本文の節は「主張の見出し + 小見出し + 入れ子の箇条書き」

- `##` の見出しは名詞だけの話題名にせず、決めたことや分かったことを言い切る文にする。判断に通し番号を振って同じ型で並べない
  - 名詞の見出しのままでよいのは、冒頭の結論の節と、表と前置きの 1 文だけを配置する節 (下の「表にするもの」の表、用語の対応表、比較表など) だけ。表だけの節に「〜は次のとおり」のような、主張を含まない文の見出しを作らない
- 節の中は `###` の小見出しで区切る。小見出しは内容に合わせて「決めたこと」「理由」「前提」「対象」「制約」「対象外」などから選択する。1 つの小見出しの下で話題が 3 つ以上に分かれるなら `####` を使う
  - 背景 (今の作り) の小見出しを、全部の節に同じ型で作らない。節ごとに背景を記載すると、読み手は決定と背景を行ごとに見分ける必要がある。背景は、決定の理由として必要な 1 文だけを理由の中に記載し、まとまった説明は 1 か所 (文書の末尾の付録など) に集める
- 並列する事実・条件・手順は 1 行 1 論点の箇条書きにする。理由・条件・例外が 2 つ以上あるときは、親の行に結論を記載し、下の階層に 1 つずつ並べる。並列の項目が 1 行に「・」で 4 つ以上並ぶなら下の階層へ分ける。表の 1 つのセルも同じで、別の話題 (条件と例外、2 種類の期限など) を 1 つのセルに入れず、行か列を分ける。項目数が少なくても、話題が混ざると読み手はどこまでが 1 つの決まりかを自分で分けることになる
- 同じ段の箇条書きが並ぶときの項目数の目安は `PRINCIPLES.md`「文書全体の読みやすさ」の 12 を定義元にする。判断を伝える文書は、そこで定めた目安に従い、意味のまとまりで小項目に分けて、まとまりの名前を親の行にする
- 「課題: / 決定: / 理由:」の見出し語を全部の行に記載した箇条書きを、節ごとに同じ型で繰り返さない
- 冒頭の要約、表や図の前置き、因果関係・判断理由・経緯を順に説明する内容は段落で記載する。改行や文の数だけを理由に、箇条書きや下位の階層へ変えない

### 表にするもの

- 対象ごとに扱いが分かれるもの (利用者の種類・操作・環境のように、同じ決定でも対象によって結果が違うもの) は「対象 / 扱い / 理由」の表にする
- 受け入れたリスクは本文の各所に散らさず、「リスク / 受け入れる理由」の表に集める。1 つの表が `PRINCIPLES.md` 12 の目安を大きく超えるときは、同じ見出しの下で種類ごとに表を分ける。理由の列には決定の言い直しでなく、なぜ受け入れてよいかを記載する
- 決まっていない事項は「事項 / 決まったときの影響 / 決める人」の表にする
- 本文で業務の言葉に置き換えた識別子 (API / 設定 / table の名前) は、末尾の「本文の言葉 / 実装の名前」の表で対応させる。読み手がエンジニアだけの設計書は、識別子を本文にそのまま使う (`design-doc-protocol.md`「散文から実装識別子を対象外にする」)

### 語と参照

- 太字は、冒頭の要約の見出し語と、各節で一番大事な決定 1 つだけにする (段ごとの使い分けは 4 節)
- 文末は文書全体で常体にそろえる (`PRINCIPLES.md`「plain JP の文体」)。冒頭の結論だけ敬体にするような混在をしない
- 動作をそのまま表す動詞で書く。意味の広い動詞 (「置」「限」で始まる動詞など) は、「保存する / 配置する」「〜を求めるのは〜だけにする」のように、何をするか・何を対象にするかが分かる文にする
- 数値は、決めた理由か出典を同じ箇所に添える。前提は、成り立たないと何が起きるかを下の階層に添える
- 「X と同じく止める」「既存の仕組みに合わせる」のように、範囲や挙動を他の仕組みへの参照だけで決めない。参照先の挙動は条件によって変わること (障害時の代わりの処理など) があるので、この文書で何をするかを条件ごとに記載する
- 同じ条件を複数の箇所で記載するときは、同じ言い方にする。片方だけを読んだ読み手が別の範囲に読まないようにする

### 書いた後の確かめ方

- 内容を知らない読み手として、別の context の reviewer に「冒頭で結論をつかめるか / 各節で決めたことと理由を読み取れるか / 7 観点の誤読」を判定させ、合格するまで修正と再判定を繰り返す (7 観点は `writing-check-protocol.md`)。繰り返す前に `writing-check-protocol.md` の「第三者の review を合格するまで繰り返すとき」を必ず Read して従う。要点は、合否を指摘の重さで決めて件数を指定しないこと、前回と逆向きの指摘が返ったら止めること、回数の上限と区切りの報告を決めておくこと
