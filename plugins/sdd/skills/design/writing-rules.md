# Design Doc の書き方の規範

`/sdd:design` が本文を組む前に読む規範。Design Doc を設計の説明ではなく、実装と検証の入力として記載する。

## 逆算の 4 原則

1. **完了の定義から始める**: 「実装が終わった」と言える条件 (受け入れ条件) を先に表で並べる。条件に `AC-1` のような ID を振らない。後続のステップから条件を指すときは、原文の文で引用する。PRD の条件は PRD の番号で参照し (番号が無ければ条件の文で引用する)、Design Doc には PRD に無い条件だけを記載する。DD の決定が PRD の条件と両立しないときは、その PRD の条件と、代わりに従う DD の節を受け入れ条件の冒頭に列挙する (どちらで完成とみなすかが読み手に決まらないため)。本文はこの条件を満たすための説明として記載し、どの条件にも対応しない節は削る
2. **実装者が迷う点だけ決める**: データ / API / 画面 / 権限 / 失敗時 / 移行 のうち、実装者が code を読んでも決められない点を「決定事項」に記載する。実装の書き方 (層の分け方 / 関数名 / 読み込み済みの再利用) は含めない
3. **検証できない仕様は記載しない**: 受け入れ条件は「〜のとき、〜が〜になる」の形で、test か手動の確認で真偽が決まる文にする。「適切に」「必要に応じて」を使わない
4. **後続のステップへ渡せる形にする**: `/sdd:plan` が受け入れ条件を文の引用で Phase に割り当て、`/sdd:implement` が完了報告で満たした条件を返し、`/sdd:review` が条件ごとに実装と test の有無を照合する。条件の総数と本文の説明が一致していることを、完成前に確かめる

## 利用者が仕様を理解できる文章

読み手は実装者だけでなく、機能を決める利用者本人でもある。

- **振る舞いは「誰が / 何をすると / どうなる」の形にする**: 主語を利用者か system の具体名にし、1 文に 1 つの結果だけを記載する (例: 「管理者が在庫を 0 にすると、商品一覧はその商品を表示しない」)
- **識別子を本文から除く**: table 名 / column 名 / endpoint / class 名は「決定事項」の表と Appendix にまとめ、振る舞いの説明には日本語の名前を使う
- **用語は初出で説明する**: 略語と社内用語は「用語」節で 1 行ずつ定義し、本文では定義した語だけを使う
- **前提、結果の順に並べる**: 条件が複数あるときは、条件を先に並べてから結果を記載する。例外や境界 (0 件 / 上限 / 同時実行 / 再送) は、通常の振る舞いの直後に下位の 箇条書き で置く
- **段落より箇条書き**: 振る舞いと決定事項は 箇条書き と字下げで並べ、段落は採用理由の説明だけに使う

## 文書全体の読みやすさ (構造ゲート)

本文の前に見出しを決め、見出しごとに役割と所有する主張を決める。文や単語を修正する前に、見出しと各段落の主張だけを追い、次の 6 点を確かめる。

1. **読む目的を 1 つにする**: 調査記録、意思決定、実装手順のように、読後の行動が変わる内容は文書を分ける
2. **結論の置き場所を 1 つにする**: 結論と理由を所有する節を決める。概要は結論を探す入口にとどめ、別の節の説明を言い換えて繰り返さない
3. **同じ問いへの選択肢を比べる**: 候補は同じ決定対象に答える形へそろえる。複数の独立した判断を 1 つの案にまとめず、判断ごとに分ける
4. **現在の状態を記載する**: 完成稿には現在の事実と判断を記載し、執筆中の訂正や調査の順序を含めない。不採用の理由や判断に必要な前提の変更は、証拠なので記載する
5. **同じ対象を同じ用語で呼ぶ**: 同じ対象を意図なく言い換えない。似た語が別の状態や対象を指すときは、冒頭で違いを定義する
6. **因果を順に追える形にする**: 主体、条件、原因、結果の対応が一度で追えない箇所だけ、文や段落を分ける

字数、文数、節の数は、この確認の合否に使わない。

## 抽象化で削らないもの

`SKILL.md` の「抽象度の上限」で削ってよいのは実装の細部だけにする。次は抽象度を上げても削らず、決定の隣に記載する。

- 決定の理由と、その決定で受け入れるリスク
- 数値 (上限・期間・しきい値) の根拠。根拠が出典に無い値は、その値を決めた出典の名前を添える
- 本文で数や種類として扱う語の定義 (「4 種類」の 4 つが何か)
- 前提が成り立たなくなったときに起きること

節や表 (未定事項の表、比較の節など) をまるごと削除するときは、削除する前にその節にしか無い理由・リスク・定義を探し、本文の該当する決定へ移動してから削除する。理由がその表の列にしか無いことが多く、表と一緒に消えると「なぜそう決めたか」が読めなくなる。

## 画面の動きは DD で決めない

画面の遷移、操作の後に戻る画面、入力を別の画面へ移動させるかは UI/UX の判断で、デザインで決める。DD はこれらを決定として記載せず、次の形で扱う。

- 未定事項に記載し、決める人をデザイナーと PRD の作成者にする
- その決定で工数が変わるなら、選択肢ごとの作業の違いを添える
- サーバーの判定や API がその決定に左右されないなら、そのことを記載し、デザインを待たずに作れる範囲を示す
- デザイン資料があれば、決まっていることと決まっていないことを分けて記載する

## 読み物として読める構成 (見出し・入れ子・表・強調)

文単位の誤読の確認に合格しても、同じ型の箇条書きや長い段落が並ぶと、読み手は「何を言いたい文書なのか」をつかめない。DD は次の形で書く。

### 冒頭で結論を言い切る

- 最初の節 (「この DD で決めること」など) に、DD 全体の結論を太字の見出し語つきの数行で記載する。見出し語は「何を解決するか / どう解決するか / 何が変わるか / いつ切り替えるか」のように、読み手が読み終えた後に答えられるようになる問いにする
- 数値や種類が並ぶ結論は、1 行に詰めず下の階層の箇条書きに分ける
- 要件は PRD にあること、細部は作業計画で決めること、識別子は末尾の対応表にあることを、引用 (`>`) の 1 段落で示す
- 判定や分岐の流れの図は、冒頭の節の中に小見出しを作成して配置する。図の上に問いを太字の 1 行で記載し、色の意味などの凡例は図の下の入れ子の箇条書きにする

### 本文の節は「主張の見出し + 小見出し + 入れ子の箇条書き」

- `##` の見出しは名詞だけの話題名 (「保存先」「対象」) にせず、決めたことを言い切る文にする (例: 「〜は、〜で判定する」「〜は、〜と分けて記録する」)。判断に通し番号を振って同じ型で並べない
- 節の中は `###` の小見出しで区切る。基本は「今の作り」「決めたこと」「前提」で、内容に合わせて「対象」「制約」「対象外」などの小見出しを使う。1 つの小見出しの下で話題が 3 つ以上に分かれるときは `####` を使う
- 本文は段落にせず、1 行 1 論点の箇条書きにする。理由や条件や例外が 2 つ以上あるときは、親の行に結論を記載し、下の階層に 1 つずつ並べる。並列の項目が 1 行に「・」で 4 つ以上並ぶなら、下の階層へ分ける
- 「課題: / 決定: / 理由:」の見出し語を全部の行に記載した箇条書きを、節ごとに同じ型で繰り返さない。見出し語は小見出しで足りないときだけ使う
- 段落のまま記載するのは、冒頭の要約と、表や図の前置き 1 文だけにする

### 表にするもの

- 対象ごとに扱いが分かれるもの (利用者の種類・操作・クライアントのように、同じ決定でも対象によって結果が違うもの) は「対象 / 扱い / 理由」の表にする
- 受け入れたリスクは、本文の各所に散らさず、「リスク / 受け入れる理由」の 1 つの表に集める。理由の列には決定の言い直しでなく、なぜ受け入れてよいかを記載する
- 未定事項は「事項 / 決まったときの影響 / 決める人」の表にする

### 強調と語

- 太字は、冒頭の要約の見出し語と、各節で一番大事な決定 1 つだけにする。用語の初出や小見出しの代わりに太字を使わない
- 動作をそのまま表す動詞で書き、意味の広い動詞を避ける。何をするか、何を対象にするかが主語と動詞で分かる文にする (例: 「保存する」「配置する」「〜を求めるのは〜だけにする」)
- 数値には、決めた理由か出典の名前を同じ箇所に添える。前提 (切り替えの設定や既存の仕組みが特定の状態であることなど) には、それが成り立たないと何が起きるかを下の階層に添える

### 書いた後の確かめ方

- 内容を知らない読み手として、別の context の reviewer に「冒頭で結論をつかめるか / 各節が今の作り、決めたこと、理由の順で読めるか / 読み違えの原因になる箇所 / 内容の正しさ」を判定させ、合格するまで修正と再判定を繰り返す (`SKILL.md` の Step 7.6)

## 文章の自己点検 (書き出した後)

次の 5 項目を当て、当たった箇所だけを書き換える。事実、時制、因果関係、主体は変えない。

1. 各節の最初の文が、その節の結論になっている
2. 1 文に論点が 1 つだけある
3. 「適切に」「必要に応じて」「柔軟に」のような、判定できない語を使っていない
4. 同じ対象を、節ごとに別の語で呼んでいない
5. 入力や確かめた資料に無い数値・事例・理由を作っていない
